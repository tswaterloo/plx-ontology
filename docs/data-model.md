# Data model

The Workbench stores business records as one typed graph, not as a table per business
object. This page explains that graph, the Prisma view of it and the typed Python models
built on it, and why the bulk paths stay SQL.

## The generic graph (Postgres, schema `ontology`)

| Table | Holds |
| --- | --- |
| `objects` | one row per source record: `object_id` (`<Type>:<binding>:<key>`), `object_type`, `audience_key` (who may read it) |
| `object_versions` | each captured version of an object: the `l1_handle` it was read from, `lineage`, `markings`, `recorded_at` / `superseded_at` |
| `value_sources`, `value_cells` | the property values of a version; `value_fields` names the property and field path, `value_kinds` the value type, unit, currency rule and markings |
| `link_rows` | typed links between objects (`link_type`, `tier`, the reason and evidence); `ontology.links` is the readable view |
| `identifiers` | normalized identifiers (PO numbers, lot numbers) pointing at objects |
| `events`, `event_objects` | dated business events and the objects they relate |
| `text_fields`, `text_chunks`, `chunk_words` | document text and its word index |

What the types *are* is not in the database. It is declared in JSON:
`ontology/schema/domains/*.json` declares 88 object types (properties with value types,
units, currencies and markings) and 397 link types (from, to, name, reverse name,
cardinality). `ontology/schema.py` compiles these with the generated and derived
types into the schema the projection and the read tools use. A new property or link is
a schema change, not a migration.

Every row carries its permission facts: `audience_key` on objects, `markings` on
versions, values and links. The read tools apply a reader's policy to them inside each
query (`operating/ontology_tools.py`, `operating/pg/ontology_reader.py`). The search
schema (`search.chunks`, `search.entities`) holds the same audience and markings
columns.

## `prisma/` (the Prisma view)

`prisma/schema.prisma` describes the real Postgres tables (`ontology`, `search`,
`plx_meta`) the way `prisma db pull` would. `prisma/app/<store>.prisma` does the same
for each SQLite app store (approvals, sessions, work log, capture stores). One file per
store, because each store is its own SQLite file. The Workbench does not run Prisma
Client: these files are documentation that Prisma users can read.

* Generated by `python3 tools/gen_prisma.py pg --scratch-cluster [--from-dump PATH]` and
  `python3 tools/gen_prisma.py app`. The pg run starts a throwaway cluster on a private
  unix socket, builds the migrations, optionally restores a structure-only dump beside
  them, and writes only when the two agree. Output matches `prisma db pull` and passes
  `prisma validate` and `prisma format` (checked with Prisma 6.19 outside the repo).
* The database declares no foreign keys, because the graph is written set-based. The
  references the code relies on (a version's object, a cell's source, a link's ends)
  are written as relations under `relationMode = "prisma"`, each commented as not
  enforced.
* Anything Prisma cannot express is kept as a `///` comment rather than dropped:
  check constraints, partial and expression indexes, operator classes, collations,
  triggers and vector sizes.
* Production has one index that no migration creates (`value_cells_by_field`), listed in
  `PRODUCTION_ONLY_INDEXES`. The byte-order twins `link_rows_by_id` and
  `object_versions_by_object_c` go with migration 0018 (GROWTH-AUDIT F7) where the
  database's default collation is byte order.
* `tests/test_prisma_schema.py` fails when a migration or a declared store changes and
  the files were not regenerated.

## Typed models (`operating/typed_graph`)

`tools/gen_models.py` generates `operating/typed_graph/models.py` from the schema. It
writes one frozen dataclass for each declared type and for each type the declared links
reach (204 in all). Each property becomes a field that holds a `Cited` value: the typed
value (`Money` with its currency, `Quantity` with its unit and role, `datetime.date`,
`Decimal`), its citation (the captured version and field path) and its markings. Each
link end becomes a method named after the link:

```python
from operating.typed_graph import GraphRepository
from operating.typed_graph.models import PurchaseOrder

repo = GraphRepository(host_tools, actor)        # the host's tool table, one reader
po = repo.get(object_id, PurchaseOrder)          # None if this reader cannot see it
po.total_cost.value                              # Money(amount=Decimal(...), currency="CAD")
for line in po.lines():                          # PurchaseOrderLine.line_of, reverse: many
    line.line_of()                               # N:1 forward: one object or None
    for receipt_line in line.receipt_lines():
        lot = receipt_line.received_lot()
```

* **Reads use the tools only.** The repository calls the reader's own `plx.object` and
  `plx.around`. Audiences, markings, the item gate, people exclusion and as-known-at
  therefore apply exactly as they do for every other answer. It has no SQL and no
  permission rule of its own. A record the reader may not see comes back as `None`,
  exactly like a missing one. A value the reader may not see leaves its field `None`
  and is counted in `withheld`.
* **Cardinality is respected.** A to-one end (forward `N:1`/`1:1`, reverse `1:N`/`1:1`)
  that reaches two objects raises `CardinalityError`; it never picks one. Lead-tier
  links are never followed. A to-many end returns a `Related` list with `complete` and
  `withheld`.
* **It fails closed.** An unknown type, property or value type raises `SchemaMismatch`,
  which means the models need regenerating. A value that does not parse (an undeclared
  enum member, an amount that is not a number) keeps its `raw` text, gets a `problem`,
  and has value `None`. When values of one property disagree, the field is `None` and
  the property is listed in `conflicts`. All values stay in `values`.
* `python3 tools/gen_models.py --check` (also run by `tests/test_typed_graph.py`) fails
  when the schema changed and the models were not regenerated.

## Which API reads use the models, and which do not (AUDIT3-09)

These operator_api reads go through `GraphRepository`: `backend.record_facts`,
`backend.record_lines`, `backend.form_sources` and `backend.style_facts` (with
`operating/doc_fill.py` and `operating/doc_gather.py`). They read a named type's typed
values and follow declared links. The reads below call the reader's own `plx.object` and
`plx.around` directly. Each one applies the same audiences, markings, people exclusion and
as-known-at as the repository would, because the repository calls the same two tools. They
stay direct for the reason given. `tests/test_data_model_reads.py` fails when a direct read
is added to operator_api without a row here, or when a row names a read that is gone.

The three reasons:

* **label**: the read needs only a record's display, a few named properties, or whether
  this reader can open it at all. It uses the tool's concise read, or `properties=[...]`.
  `repo.get` would read every value page (`detailed`), and it would raise
  `SchemaMismatch` on a property the models do not declare. A page or a label would then
  fail where today it shows a name.
* **generic**: the link or the type is chosen at run time. Examples are a record's
  `<Type>.same_record_as` copies, the links of any record on the explorer, the
  verified-tier floor, or the one-edge existence check of a fulfilment link. The
  repository follows declared links of a known model. It reads one detailed object for
  every neighbour (`many`) and has no `tier_floor`. The direct read stays one round trip.
* **as-known-at**: the read is of the record as it was known at an earlier time. The
  repository reads the current record only.

The SQL left in operator_api reads no business records. It reads three kinds of table.
Store metadata covers `store_meta`, `ontology.load_state` and the freshness rows. Search
covers the `search.entities` trigram match and the `search.chunks` emptiness check. The
rest are the API's own stores: `memory`, `work_log`, `templates`, `feedback`,
`page_store`, `trust`, `learning_memory`, `write_intents_api` and `autopilot_api`. Those
are app tables. The rules in the next section apply to them.

## App tables (`operating/app_tables`)

`operating/app_tables/rows.py` (also generated by `tools/gen_models.py`) gives typed rows
for the approval and write-intent, session and work-item stores. Each table also gets a
`Table` with keyed reads only: equality on named columns (checked and quoted), bound
values, an order and a limit. These replace raw SQL where a read was a plain keyed
lookup, such as an intent's event chain or a consumed approval. The hash-chained
appends, every write, and the queries that use JSON paths or joins stay as written SQL,
because they carry the stores' invariants.

## Why bulk paths stay SQL

Loading, delta application, link building, search and aggregation all work on millions
of rows in single set-based statements (`operating/pg/ontology_load.py`,
`ontology_delta.py`, `link_apply.py`, `operating/ontology_tools_aggregate.py`). An ORM
in those paths would turn one statement into a round trip per row. It would also hide
the permission predicates the read tools put into each query. The models above are for
code that reads one object and its neighbours.
