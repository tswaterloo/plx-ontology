## 1. What MC is and owns

FACT (`AGENTS.md` "System Overview"; `docs/product/SYSTEM_OF_RECORD.md:12-29`): MC is "the human cockpit over Petra Lab-X's background agents". It has two invariants. **Everything resolves to a Task.** **SharePoint (`/sites/plx-mission-control`) is the canonical system of record for planning records**: the app is a two-way mirror with a conflict queue and an audit log. EN-007 made MC the *enforced* system of record for repo work. Every merged PR on an enrolled repo links to a task, agent PRs are gated on an evidence bundle, operator PRs are recorded but not gated, and every governed action appends to `mc_events`.

MC owns:
- **Execution records**: projects, buckets, tasks (stage, owner, assignee, evidence, approval gates), SharePoint mirror and conflicts.
- **Agent dispatch credentials**: checkouts `dsp_*`, an 8 h TTL that holds while the PR stays open (`src/lib/compliance/service.ts:57-59`).
- **The compliance gate**: the GitHub `compliance` check on tracked repos via `/api/compliance/verify`, with risk tiers low/standard/high (`docs/product/SYSTEM_OF_RECORD.md:122-135`). High tier needs an https PRD link (TASK-2112) and `testRun` or `shots`.
- **Runtime approval gates** (TASK-629/630).
- **The append-only event log `mc_events`**: "the Second-Brain substrate" (`db/migrations/008_compliance.sql`).
- **MCP principals and the permissions kernel**: deny-by-default, `permissions.v2` (`src/lib/permissions/authorize.ts`).
- **Skills directory**, routing (PR → task suggestion/proposal), vendor spend, governance contract generation for all tracked repos.

## 4. Authority, approval and governance model

**Authentication** (`src/lib/mcp/auth.ts`, FACT):
1. `PLX_MC_MCP_ENABLED=1` must be set server-side, else 503.
2. The key is read from `x-api-key` or `Authorization: Bearer`. Since `feec59d` #306 TASK-619 (`auth.ts@2f653cf`) it is compared, by constant-time SHA-256 digest, against every credential slot at once: each principal's key in the per-agent registry `PLX_MC_MCP_AGENT_KEYS` (JSON `{principalId: key}`, unknown ids ignored), an optional `next` key per principal from `PLX_MC_MCP_AGENT_KEY_ROTATIONS` (`{principalId: {next, currentEnabled, nextEnabled}}`, both flags default true, only for principals in the base map), and the legacy shared `PLX_MC_MCP_API_KEY` → `sp_mcp_cursor`, enabled while `PLX_MC_MCP_SHARED_KEY_ENABLED` is `1` (default; any other value disables it).
   - **Rotation overlap:** during an operator-run window the current and the next key both resolve to the same principal. `currentEnabled=false` rejects the old key, `nextEnabled=false` the new one; the operator then promotes `next` into the base map. MC audit shows no key change: both slots carry one principal.
   - **Fail closed:** a disabled slot wins over an identical enabled one (401 `invalid_api_key`, `key_revoked` in `permissions_decision_log` when enforcement is not off). A key shared by two principals matches none (401). A malformed rotation config refuses every key with 503 `mcp_key_config_invalid`. No enabled slot → 503 `mcp_key_not_configured`. No match → 401 `invalid_api_key`.
3. `x-mc-operator-email` is required and **must be on `PLX_MC_ALLOWED_USERS`** (403 `operator_not_allowed`). It is an admission gate, not only audit. Since `5d0c206` #338 TASK-3010 the same list is only the transitional / break-glass path for human sign-in (people are admitted by the Entra app roles `MC.Owner`/`MC.Admin`/`MC.Member`, which write `mc_users` at sign-in), but it stays the MCP operator allowlist: the operator steps reduce it to the MCP operator emails plus a named break-glass owner, never to empty (`docs/modules/permissions/README.md:155-203,237-238@5fdf375`, `docs/FLEET-SECRETS-SOP.md:77@5fdf375`; `src/lib/mcp/auth.ts` unchanged since `8cd548a`). Our `MC_OPERATOR_EMAIL` must stay on that reduced list, or every Workbench MC call is 403. `x-mc-repo` is required; since `a96be68` #282 TASK-1958 a value outside `ACTIVE_TRACKED_REPO_SLUGS` is logged (`mcp.repo_not_allowlisted`, log-only, `auth.ts:148-158@eeb7db7`). Planned enforcement would answer 403 `repo_not_allowlisted`, which our honest `tswaterloo/OntologyProject` label would hit: every MC call would then fail closed until the label is allowlisted (Vince). `x-mc-runtime` defaults to `cursor` and is a free-form label. `x-mc-worker-id` is optional.
4. The principal is loaded from `service_principals`. From enforcement mode `review` onward, a missing or revoked principal fails closed and, since `4e82fc3` #279 TASK-620, is recorded as a denial in `permissions_decision_log` (as are tool-allowlist denials and agent-assignee decisions) (`PLX_MC_PERMISSIONS_ENFORCEMENT_MODE` off/log-only/review/enforce, default off: `docs/modules/permissions/README.md`).
5. Since `d9e08c2` TASK-3407 a caller may send `X-MC-Agent: <runtime>/<lane>`; it must match `<runtime>/<lane>` and start with the `X-MC-Runtime` value, else 400 `invalid_agent` (`src/lib/mcp/auth.ts:227-236@2d2cac7`). The audit actor becomes `<runtime>/<lane>:<operator>`, else `<runtime>:<operator>` as before (`mcpAuditActor`, `auth.ts:45-46@2d2cac7`), and `mcp.tool.invoked` records `agent` (null when absent; `src/lib/mcp/audit.ts:28@2d2cac7`, `24a06ce`). The Workbench sends no `X-MC-Agent` (`WB:integrations/mc.py` headers: operator email, repo, runtime `plx-operating-platform-read`), so its calls and audit rows are unchanged; the header is only required, and only when `PLX_MC_CHECKOUT_AGENT_REQUIRED=1`, for `mc_checkout_task`, which the Workbench never calls.

## 8. Concrete integration recommendations (goal 2)

**R1. Two clients, one allowlist.** Keep REST (`WB:integrations/mc.py`) for reads. It returns `meta.actor` for repo and principal checks. Use MCP JSON-RPC only where an agent needs tools. In Workbench code, enforce allowlist A = tools #1–#12 (the **R** rows). Everything else is refused unless an approval record from the operator or Vince names that exact call. Never call the **NO** rows.

**R2. Exact call shape** (stateless; each POST stands alone; send both Accept types, which the SDK Streamable HTTP transport expects. INFERENCE from the SDK, confirmed in practice by the 200 on `initialize`):

```http
POST https://mc.plxcustomer.io/api/cursor/mcp
Content-Type: application/json
Accept: application/json, text/event-stream
x-api-key: ${MC_MCP_API_KEY}
x-mc-operator-email: ${MC_OPERATOR_EMAIL}      # must be on PLX_MC_ALLOWED_USERS
x-mc-repo: tswaterloo/OntologyProject          # honest audit label; for checkouts pass repo= explicitly
x-mc-runtime: plx-workbench

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"mc_get_task","arguments":{"id":"TASK-477"}}}
```

Parse `result.content[0].text` as JSON:
- Some tools return `{data, meta}` (`mc_get_context`, `mc_search_tasks`, `mc_get_task`, `mc_list_checkouts`, `mc_search_knowledge`, `mc_verify_pr`, `mc_list_conflicts`, `mc_request_approval`).
- Others return a bare object (`mc_self_check`, create/checkout/progress/complete, skills, routing, resolve/dismiss).
- `result.isError` → `{error:{code,message,hint?}}`.
- HTTP non-200 → `{error:{code,message}}`, auth layer.

REST equivalents:
- `GET /api/cursor/tasks?q=&bucket=&stage=&assignee=&limit=`
- `GET /api/cursor/tasks/TASK-477`
- `GET /api/cursor/knowledge/search?q=&limit=`
- `GET /api/cursor/verify?repo=petralabx/PLX_MC&pr=267`

All take the same four headers.

**R3. Goal-2 flow (the authorized action envelope).** Steps marked W-A need explicit human approval before the *Workbench* sends them; MC's own gate is a second, separate approval.

1. Ground the objective (read): `mc_search_tasks{q:"<objective terms>", limit:20}` → `mc_get_task{id}`, then `mc_get_context{depth:"compact"}`, then `mc_self_check{}`. Refuse to act if `dataSource != "live"` or the boring gate fails.
2. Record the work (W-A): `mc_create_task{title, bucket:"<BKT from mc_list_buckets>", reporter:"<operator>", description:"<objective + Workbench case link>", priority:"medium", idempotencyKey:"wb-<objective_id>-<n>"}`. Store the returned `taskId`. A replay is safe.
3. Ask a human (W-A): `mc_request_approval{taskId, reason:"<≤500 chars: exact action, target system, record ids, reversible?>"}` → `gateId`. Poll `mc_get_task{id}` until `approvalGates[gateId].status` is `approved` or `rejected`. Record `decidedBy` and `decidedAt`. With a `rejected` gate or none, take no action.
4. Execute only in the owning system, through its own authorized interface. Today no Portal/BC write interface is authorized for us, so this step stays empty, or a human does it from a Workbench-prepared packet.
5. Journal (W-A): `mc_report_progress{taskId, stage:"<explicit>", notes:"<what was done + read-back verification>", progressPct}`. Always pass `stage` or `notes`. Since #298 TASK-2560 MC refuses it (403) unless our principal holds an active checkout of the task, so this step needs step 6's checkout or the agent report alone. Then `POST /api/cursor/agent-report{agentSlug:"plx-workbench", loopId:"<campaign>", runId:"<run uuid>", title, markdown}`, which is idempotent per runId.
6. Code changes to petralabx repos only: `mc_checkout_task{taskId, repo:"petralabx/<repo>"}` → draft PR with `prBodyLine` → `mc_complete_task{checkoutId, summary, verificationCommands:[...], rollback:"...", prUrl, commitSha}` → `mc_verify_pr{repo, pr}`. This is an "upstream PLX repo change" and is out of bounds under current Workbench rules unless explicitly approved.

**What a write grant on one bucket needs (re-read 2026-10-19 at `9b4b19f`; INFERENCE where marked).** MC cannot express it today. A grant is a list of capabilities per principal, with no bucket in it (`src/lib/permissions/grants.ts:130-133,144-173@9b4b19f`).
